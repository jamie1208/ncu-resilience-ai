# ADR-0012：G1-2 只計網路正常時段，改為人工閘門；豁免 2026-10-18 一晚的結果

- 狀態：已採納
- 日期：2026-10-19
- 決定者：使用者本人（2026-10-19 在對話中明確同意）

## 背景

1. P1-T10 的第一次一晚運行（2026-10-18 22:45 起）中，**本機網路在 2026-10-19 04:13–10:43 中斷**：
   - 所有連網來源都是 `ConnectError`，連氣象署 API 也一樣；
   - 08:00 的 Facebook 排程回報 `ENOTFOUND`；
   - 電腦沒有睡眠（`caffeinate` 持續了 14 小時）；
   - 原始成功率 59.6%，未達 G1-2 的 98%。
2. 中斷期間，P1-T08 的自動停用機制把 8 個來源停用；網路恢復後也不會自動重新啟用，因此出現長時間的空檔。這個問題已經在 P1-T10 修正：可重試的失敗不再計入自動停用。
3. G1-2 原本是自動閘門，指令會計算「執行當下往前 12 小時」。結果會隨執行時間改變，無法固定評估某一晚。
4. 使用者在個人環境（家用網路）運行本系統，夜間網路中斷不是程式可以控制的。

## 決策

1. **G1-2 改為「網路正常時段內成功率 ≥ 98%」**，全網中斷時段由程式依客觀規則偵測（`backend/app/ingestion/report.py`）：
   - 連網來源（`manual_import` 以外）的有結果執行依時間排序後，連續的連線失敗（`SourceUnavailableError`）且涉及 ≥ 2 個來源，範圍是第一筆到最後一筆失敗；中間只要有一次成功就斷開；
   - 只排除中斷時段內連網來源的失敗；單一網站自己的失敗、版型改變等其他失敗一律計入；
   - 連續性在計算間隔時，扣掉與中斷時段重疊的部分；
   - 報告同時列出原始成功率、中斷時段與排除的次數，供人工檢查。
2. **G1-2 改為人工閘門**：判定依據是 `docs/progress/records/P1-stability.md` 記錄的運行結果。`scripts/reports/ingestion_report.py --hours 12 --check-success 0.98` 保留，用於重跑與查證。
3. **豁免 2026-10-18 一晚的結果**，認定 G1-2 通過（使用者決定）：
   - 依新規則：成功率 **100.0%**（65／65），中斷時段 04:13–10:43（排除 44 次），重複寫入 0；
   - 依新規則仍有 2 個來源不連續（cwa-alerts、ncu-announcements）：網路 10:43 恢復後，到 12:40 重新啟用之前都處於停用狀態，空檔 1 小時 48 分。這是已修正的自動停用問題造成的；
   - 報告數據照實保留，不修改。

## 考慮過的替代方案

- **重跑一晚**：自動停用已經修正，可能可以正常通過，G1-2 也能維持自動閘門；但使用者決定不重跑。
- **只排除中斷時段、維持自動閘門**：這一晚仍然因為連續性不通過，而且自動閘門的結果會隨執行時間改變。
- **維持原定義**：家用網路的夜間中斷會讓 G1-2 很難穩定達標，而失敗的原因與系統品質無關。

## 影響

- G1-2 從自動判定改為人工確認，也放寬了判定條件（排除網路中斷），這兩點都是使用者同意的放寬。
- 之後如果要重新驗證穩定性（例如部署環境改變），可以用同一個指令重跑，並把結果附在 `P1-stability.md`。
- 偵測規則可能把「兩個網站剛好同時故障」誤判為全網中斷。報告會列出中斷時段，人工確認時要檢查。
