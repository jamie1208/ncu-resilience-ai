# ADR-0011：Facebook 貼文改以內文雜湊識別，不取單篇網址（P1-T13）

- 狀態：試行
- 日期：2026-10-18

## 背景

1. P1-T13 原本的設計是：以貼文的固定網址（`/groups/NCUgroup/posts/<編號>`）作為 `external_id` 去重，並作為 G1-4「可反查原文」的依據。
2. 2026-10-18 在使用者的 Chrome 中實測三次（`claude -p --chrome`），都取不到單篇網址：
   - 貼文時間連結剛載入時只有追蹤參數（`?__cft__…`），沒有貼文路徑；
   - Claude in Chrome 擋下含追蹤參數的網址（`[BLOCKED: Cookie/query string data]`）；
   - 懸停後讀取連結的 `pathname`，又被擋下（`[BLOCKED: Base64 encoded data]`）。
3. 這些阻擋是擴充功能的安全機制。再改用其他方式讀同一份資料，等於刻意繞過它；逐篇點開貼文頁則會增加被 Facebook 判定為自動化的風險。這兩種做法都不採用。

## 決策（使用者決定「先用 C 試試看」，2026-10-18）

1. **擷取端完全不讀連結**（不懸停、不點擊），只讀頁面上看得到的內文與發文時間。
2. 每筆的 `url` 填社團網址（`config/sources.yaml` 的 `source_url`），不填 `external_id`。
3. `manual_import` 新增來源選項 `derive_external_id`（預設 false；facebook 設為 true）：項目沒有 `external_id` 時，由匯入程式計算
   `external_id = "content-" + sha256(內文前 300 字，連續空白合併為一個).hexdigest()[:40]`。
   - 不把時間放進雜湊：相對時間（「3 小時」）換算有誤差，加入時間反而會讓同一篇算出不同的識別碼；
   - 同一檔案中內文相同的貼文視為同一篇，只保留第一筆；明確給的 `external_id` 重複時，仍然整檔拒絕。
4. 這是**試行**：先觀察一週的去重效果與資料品質，再決定繼續、改成手動匯入（附單篇網址），或兩者並用。

## 影響

- **G1-4 對 Facebook 資料不成立**：資料庫只能追溯到社團與發文時間，無法連到單篇貼文。G1-4 抽樣時排除 `facebook` 來源，並在閘門紀錄中註明。
- **編輯過的貼文會變成新的一筆**：前 300 字改變時，識別碼也會改變。重複的事件由 S04（同事件合併）處理，標記時要注意。
- **內文相同的不同貼文會被合併**：例如兩個人都只貼「停電了？」。社團中少見，影響很小。
- 發文時間仍然寫入 `published_at`，但精確度只到擷取端能讀到的程度。
- 擷取端不再需要 `find`、`read_page`、懸停與 `pathname` 的例外規則，這些都從 skill 中移除。

## 考慮過的替代方案

- **逐篇點開貼文頁**：可以取得網址，但頁面載入次數多、風險高，而且實測時點擊後網址沒有改變。
- **手動匯入（附單篇網址）**：可追溯性最好，但不是每天自動執行；保留為試行失敗後的備案。
- **把時間加入雜湊**：時間讀不準時，去重會失效。
