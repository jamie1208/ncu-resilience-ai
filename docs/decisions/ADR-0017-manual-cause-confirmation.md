# ADR-0017：人工確認原因後，相關學校措施可以公開

- 狀態：已採納
- 日期：2026-11-04
- 決定者：使用者本人（新增功能、公開頁不標示來源）；實作細節由 AI 決定並記錄於此
- 部分被取代：決策 4 的第 1 點（疑似指控事件人工確認後仍不公開內容）被 ADR-0018 取代，P8-T06 起生效
- 補充：ADR-0015 第 3 點「S07 的推測原因（`hypothesized`）不公開」

## 背景

公開版小報告只放影響與建議，不放原因本身；但措施若依據推測原因（`cause_basis` 為 `hypothesized`），公開規則（P5-T10，`app/publishing/policy.py` 的 `_public_measures`）會整項濾掉。學校措施大多是「查明原因」或「預防再發生」，幾乎都綁著 S07 的原因；而 S07 只有在 `ncu-` 校方來源明確寫出原因時才判 `confirmed`。

2026-11-04 公開中的 13 個事件有 3 個只顯示「同學可以做」：它們都已查證、證據全部來自 Facebook，學校措施的依據全是推測原因。重新產生小報告不會改變結果，因為 S07 的判定只看證據來源與內容，不看事件查證狀態。

使用者可能已經用其他管道（例如向權責單位詢問）確認了原因，但系統沒有地方記錄這件事。

## 決策

1. **新增「人工確認原因」**（使用者決定，P7-T07）：管理者可以在後台把最新一份有效小報告中的推測原因標為「人工確認」，也可以回滾到推測。
2. **公開規則的有效依據**：措施依據的原因經人工確認後，公開規則把它視為 `confirmed`，這些措施就可以公開。原因本身仍不公開（ADR-0015 不變）。
3. **公開頁不標示來源**（使用者決定）：經人工確認而公開的措施，顯示方式和依據校方來源確認的措施相同。
4. 不變的硬性邊界（AI 決定，寫在程式裡、設定無法關閉）：
   - 疑似指控的事件仍不公開內容，人工確認不能繞過指控規則；
   - 措施文字仍經 PII 遮蔽，也仍納入指控規則比對；
   - 沒有人工確認的推測原因，行為和現在完全相同（G5-5 的既有測試不修改）。
5. 實作細節（AI 決定，可在 P7-T07 調整並記錄）：
   - 確認時必填「確認依據」（例如「11/5 電話向總務處確認」），最多 200 字，含個資時拒絕；
   - 確認只套用在當時那份小報告；重新產生小報告後原因代號會變，需要重新確認；
   - 確認與回滾都寫入稽核 `report.cause_decide`（metadata 只有報告、原因代號、from／to，不含依據文字）；
   - 公開狀態在下一次公開同步（每分鐘）更新；回滾後相關措施就撤下。

## 考慮過的替代方案

- **維持現狀**：完全符合原邊界，但讀者會以為學校沒有建議。
- **前端補一行中性說明**（「原因仍在查證中，學校端建議查證後才會公開」）：改動最小，但不能讓已確認的措施公開。
- **公開頁標示「原因經人工確認，非校方公告」**：較透明，使用者選擇不標示。

## 影響

- 公開內容的正確性多了一個人工環節：確認依據不足時，錯誤的措施可能被公開，責任由使用者承擔（ADR-0015「法律責任」）。確認依據與稽核紀錄是回溯的依據。
- 公開頁不標示來源，讀者無法分辨措施是依據校方公告還是人工確認。
- `docs/architecture/threat-model-public.md` 要補上這條公開路徑。
