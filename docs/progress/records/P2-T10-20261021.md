  1. **規則優先，模型只提供判斷**：
     - S05 逐份輸出證據的立場（supports、contradicts、refutes、unrelated）與陳述性質（official、first_hand、hearsay、rumor），另外給 `suggested_status`；
     - 最終狀態只由 `rules.py` 決定；模型的建議只用來記錄兩者是否一致，不會被採用。
  2. **判準沿用標記規範第 4 節**（ADR-0009）：
     - **官方來源**（`ncu-*`、`cwa-alerts`）以最新一份為準：支持 → verified；否認 → false；說法矛盾 → disputed。是否官方只看 `source_code`，不看模型的判斷。
     - **沒有官方表態時**：支持與反對並存 → disputed；兩份以上第一手來源支持 → verified；其他 → unverified。轉述與謠言不算第一手，謠言的支持也不構成爭議。
     - **規格 A08**：verified 一定附上支持的 evidence_ids，沒有就降為 unverified。
  3. **名稱**：規格的 `confirmed` 統一為 `verified`（state-machines.md，使用者 2026-10-17 決定）。
  4. **狀態變更**：一律經 `transition()`。
     - `apply_verification`：狀態沒有改變時不轉移，因為狀態機不允許自我轉移。
     - `event_status_for`：已在後續追蹤（monitoring、resolved）的事件，查證結果為 verified 或 unverified 時不改變；不合法的轉移會拋出錯誤，例如 detected → verified、resolved → false。
  5. **門檻的表示方式**：計畫的門檻是「無 evidence_ids 被標 verified 的次數 = 0」，屬於計次型，所以評測框架新增 `unsupported_count` 指標，以 `max: 0`（≤）判定。
     - 違規的定義：模型建議 verified，但沒有任何「被引用、且立場為 supports」的證據。
     - 這需要修改計畫沒列出的 `app/ai/eval/metrics.py` 與 `runner.py`，見下方的額外檔案。

## 已知限制

1. **只有這一個門檻**：
   - 計畫只列了「違規次數 = 0」。一個永遠回答 unverified 的模型也能通過這個指標；
   - 查證是否正確，目前靠 golden 全部通過，以及「規則結果等於預期」的單元測試來把關；
   - 計畫沒有 suggested_status 正確率的數值門檻，要不要加，見下方「需要人工決定的事項」。
2. **獨立性只看證據是否不同**：兩份第一手貼文就算 verified。
   - Facebook 貼文沒有作者資訊（ADR-0008），無法判斷是不是同一人發的；
   - 轉貼靠模型標為 hearsay 來排除。
3. **官方來源靠代碼前綴判斷**：`ncu-*`、`cwa-alerts`。之後若有非官方來源的代碼以 `ncu-` 開頭，要改成在 `config/sources.yaml` 標記。
4. **案例全部是自行撰寫的**，數量 28 筆；disputed 只有 2 筆，數量偏少。
5. **還沒有寫入資料庫**：`rules.py` 只有判定與狀態轉移的函式。寫入事件狀態、audit_logs 與 ai_analysis_runs 的串接，由 P2-T13 的管線負責。
