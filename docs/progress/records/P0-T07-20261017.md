## 已知限制

- **資料表擁有者或 superuser 可以停用 trigger**：目前應用程式與 migration 共用同一個資料庫帳號（擁有者），trigger 擋得住程式錯誤與一般 SQL，但擋不住有意的擁有者操作。正式環境需要分離「應用程式角色（只有 INSERT、SELECT）」與「migration 角色」，屬 P5-T06。
- 空表上的 `DELETE` 不會觸發列層級 trigger（回傳 `DELETE 0`、不報錯），這是 PostgreSQL 的正常行為；有資料時一定會被拒絕（有測試）。
- metadata 只檢查欄位名稱，不檢查值的內容；值裡若放了個資或原文仍會寫入，要靠呼叫端遵守規範。
- `record_audit` 尚未接到任何 API（P3 起各寫入端點使用）；權限遭拒寫入稽核屬 P3-T01。
- 測試資料庫的 `audit_logs` 不會被清空，會隨測試累積；測試已改為以唯一 id／request_id 篩選。
- CHECK 約束的值是 migration 當下的快照；`EventStatus` 新增值時，必須另寫 migration，`test_constraint_values_match_enum` 會偵測不一致。
