- 功能清單：
  - 送出回報時回傳一次高熵收據碼（15 bytes 隨機 = 120 位元，base32，`XXXX-XXXX-XXXX-XXXX-XXXX-XXXX`）；資料庫只存正規化後的 SHA-256（`report_receipts`），明文不落地、不寫稽核與日誌。收據碼本身已有 120 位元隨機性，不另外加鹽，也就不用管理額外的秘密。
  - `GET /api/v1/public/reports/status`：收據碼放在 `X-Receipt-Code` 標頭（使用者 2026-11-10 選擇；request 日誌會記路徑，所以不放網址，查詢字串中的收據碼也一律忽略）。只回 `received`／`processing`／`handled`，不含投稿內容；回應一律 `no-store`、沒有 ETag、`Vary: X-Receipt-Code`（`ReceiptRoute` 覆寫公開路由的快取，並移除 `If-None-Match`，不會回 304）。錯的、格式不對、過長、缺少與不存在的收據碼都回相同的 404 `NOT_FOUND`（格式不對也查一次資料庫，讓回應時間相近）。查詢有自己的限速：每個用戶端 10 分鐘 20 次（使用者 2026-11-10 決定；先改為 1 次，同日再改為 20 次）、全站 600 次；經通道時閘道轉送真實用戶端位址，所以是每個人各自計算。前端說明每 10 分鐘最多查詢 20 次，被限速時也這樣提示。
  - 狀態對應：所有投稿都還沒擷取 → received；全部分析完成（done／skipped／failed），且相關事件都已結束（resolved／archived／false）或沒有成立事件 → handled；其他 → processing。補件會一起列入計算。
  - `POST /api/v1/public/reports/supplements`：本文 `{receipt_code, content, location?}`；與投稿共用 `ReportRateLimiter`（錯的收據碼也算一次，不能拿來暴力猜碼）、同樣的 8 KiB／JSON／10–2000 字／控制字元限制、只接受這三個欄位；先檢查格式再比對收據碼，所以格式錯誤的 422 不會透露收據碼是否存在。補件寫進同一個 `anonymous_reports` 收件匣，由既有 Adapter 拉進管線（以 `<untrusted_source>` 包裹）；每張收據最多補件 5 次，超過回 409 `CONFLICT`。稽核 `anonymous_report.supplement`，只記字數、有無地點與第幾次補件。
  - 補件掛到原投稿的事件（使用者 2026-11-10 要求併入本任務）：管線分析補件時，原投稿已屬於未封存的事件 → 補件直接掛到該事件（outcome `linked`，不呼叫 S01–S04），再重跑 S05、S06；原投稿還沒擷取或在等待分析 → `deferred`（回到 pending、不計失敗次數，下一輪掃描再試）；原投稿分析完但沒有事件或分析失敗 → 照一般文章分析，但原投稿作為同一則回報的第二份證據一起交給 S01–S04（補件在前；S01–S03 的輸入本來就允許同一篇文章 1～3 份證據，SKILL.md 不變、不需重跑評測）；補件建立或併入事件時，原投稿也一起成為該事件的證據。原投稿只在使用者封存的事件中時，只當作脈絡、不帶進新事件。原投稿本身的分析流程不變。
  - 後台「來源對照」：補件的證據標「補件」並說明補充第幾則來源。後台事件詳細 API 只有補件的證據才多一個 `supplement_of`（原投稿的來源文章 id），其他證據的回應格式不變。`support_type` 會被 S05 覆寫，所以不拿它來標。
  - 事件合併後的狀態：合併時證據會移到目標事件（`app/events/merge.py`），查詢狀態本來就照證據目前所屬的事件，所以合併後看的是目標事件；新增測試確認（先前把這點列為限制是誤判）。
