計畫要求的三種情況都有測試：

- **無效 JSON**：重送一次後成功；3 次都無效時 abstain（invalid_output），紀錄的問題代碼是 `json`，不保存原始輸出。
- **不存在的 evidence_id**：3 次後 abstain，問題代碼是 `evidence`。
- **超支**：
  - 超過每次上限：不呼叫，failed（cost_limit），attempts 0、cost 0；
  - 超過每日上限：不呼叫；
  - 重試前會再檢查每日上限：第一次的實際費用加上第二次的預估超過上限，就停止。

其他測試：

- **重試與錯誤**：無效輸出立即重送；暫時性錯誤以 2、4 秒退避，也會依 Retry-After；暫時性錯誤與無效輸出共用 3 次；金鑰錯誤不重試；拒答 abstain；輸出未完成也計費並重送。
- **個資**：6 種格式都能偵測；5 種常見文字不會誤判（日期時間、民國日期、ISO 時間、分機、地震報告編號）。
- **安全**：紀錄不含來源原文、無效輸出或 SKILL.md；來源無法跳出 `<untrusted_source>`；屬性值無法注入。
- **資料表**：每日加總以台北時間 00:00 為界；status、type 有 CHECK；禁止關聯到自己；關聯不可重複；事件刪除後執行紀錄保留（event_id 設為 null）；風險評估保留歷史。

## 已知限制

1. **業務驗證只做共同規則**：skill-standard 寫的「ok 時結論欄位不可為 null」沒有通用做法，因為 S02 的地點等欄位在 ok 時也可能是 null。各 Skill 的專屬規則要在各自的任務中，用 schema 或額外檢查處理。
2. **個資規則可能誤判或漏判**：例如連續 9 位數字的訂單編號會被當成學號；不檢查人名、LINE ID。
3. **重送時不附上錯誤回饋**：無效輸出重送時使用同樣的訊息。P2-T05 評測後，如果無效率偏高，再考慮把問題代碼回饋給模型。
4. **每日上限有競態**：並行執行時，各自讀到的已花費都是同一個值，可能稍微超過上限。目前是個人使用、量小，可以接受；P2-T13 的 Celery 管線如果並行執行，要再處理。
5. **開發資料庫與 worker 映像檔**：
   - 開發資料庫要執行 `alembic upgrade head`，需要使用者同意；
   - worker 映像檔要重建（`make up`）才會包含 jsonschema；
   - P2-T13 之前不會實際用到這兩者。
