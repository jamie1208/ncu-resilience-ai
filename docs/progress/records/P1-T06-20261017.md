  - `store_items(session, principal, source_code, items, *, request_id=None) -> StoreResult`：把同一來源的一批 `NormalizedItem` 冪等寫入。
  - **`source_items` upsert**：
    - 唯一鍵為 `(source_id, external_id)`；沒有 external_id 時改用 `(source_id, url)`，對應 0001_core 的兩個部分唯一索引（`ON CONFLICT ... WHERE`）。
    - 已存在的文章：
      - 網址更新為最新的；
      - 發布時間用 `COALESCE`，不以空值覆寫已知值；
      - 擷取時間用 `GREATEST`，記錄最近一次擷取，不會倒退。
    - 用 `RETURNING (xmax = 0)` 判斷是新建還是更新，不需要先查再寫，避免競態。
  - **`source_item_versions`**：
    - 以 `(item_id, content_hash)` 唯一鍵 `ON CONFLICT DO NOTHING`，內容雜湊沒變就不新增版本；
    - `captured_at` 為該次擷取時間，可反查各版本何時取得；
    - 同一批中的重複項目逐筆處理，不會觸發「ON CONFLICT 同一列更新兩次」的錯誤。
  - **單一交易**：
    - 和 `record_audit` 一樣只 flush 不 commit，呼叫端以 `async with session.begin():` 包住整批；
    - 任何一筆失敗整批回滾，稽核紀錄也一併回滾（有測試）。
  - **寫入前的防護**（全部在寫入任何資料之前檢查）：
    - 需要 `ingestion:write` 權限，只有 `service_ingestion` 有；
    - 來源必須存在於 `sources` 表，而且核准、啟用。這和 registry 的檢查重複，是刻意的雙重防護；
    - 每一筆的來源代碼必須和寫入目標一致，`content_hash` 必須和內容相符。
  - **稽核**：
    - 每批一筆 `source_items.ingest`，target 為 `sources/<代碼>`；
    - metadata 只有筆數（received、new_items、changed_items、unchanged），不含內文；
    - 空的批次不寫入任何資料，也不寫稽核紀錄。
  - **`StoreResult`**：新文章、內容改變（新增版本）、未改變三種筆數，供 P1-T07 寫入 `ingestion_runs.counts`。

## 已知限制

- **內容改回舊版時不會新增版本**：A → B → A 時，第三次的雜湊和第一個版本相同，受 `unique(item_id, content_hash)` 限制不會新增，用 `captured_at` 排序的「最新版本」會是 B，實際上目前是 A。這是規格 §9 資料表設計的結果；公告改回原文的情況少見，需要時可以新增「最後一次看到的時間」欄位（要寫 migration）。
- 每筆文章各執行兩個 SQL（upsert 與新增版本），一批最多約 50 筆，量不大；之後量變大時再改成批次語句。
- 每次擷取都會更新已存在文章的 `fetched_at`，即使內容沒變也會寫入一次（列數不變）。
- 刪除文章（來源下架）不會反映在資料庫，屬於 P1-T08 來源健康檢查的範圍。
