### §2.1 關鍵使用情境（v1.2 期望結果）

- 社群提及疑似自行車失竊：事件**公開 AI 摘要並標「尚未查證」**；指控詞命中時同時標 `needs_review`、在通知中心提醒使用者並附一鍵下架（ADR-0018 2-1、2-2）。歸入「自行車失竊」系列，系列頁顯示件數、每週時間軸與這個系列的每一起。
- 宿舍停電公告：官方來源證實 → 快報標「已查證」；改善建議與改善進度在系列頁公開。
- 匿名通報食安疑慮：投稿原文永不公開；AI 摘要照公開規則公開並標「尚未查證」，疑似指控照原文摘要公開並即時提醒（使用者知悉妨害名譽風險後的決定）。投稿者可用收據碼查進度與補件。
- 同區域多次事件：同類別同主題的事件歸為同一系列，S12 依代表地點分組並找規律；推測的規律與原因公開在系列頁並帶「推測，尚未查證」，不認定因果；前後比較註明「變少不一定是措施的功勞」。

### §3.1 端到端資料流程

來源擷取 → 原始資料保存與版本 → 標準化 → 未分析文章掃描 → S01 相關性 → S02 事件抽取與摘要（S02 抽出沒見過的地點名稱時 → S13 判斷代表地點／上層地點）→ S03 分類 → S04 同事件／關聯 → S05 查證 → S06 風險（程式加權）→ 個人通知規則 → **S11 系列歸組**（每個事件都屬於一個系列）→ **S12 系列分析**（Celery 任務，每系列每台北日最多一次）→ 公開規則引擎 → 公開快照（事件、系列）→ 系列改善追蹤、再發生提醒（依代表地點）→ 時序統計、S09、CRI。

匿名補件：原投稿已屬於事件 → 補件直接掛到該事件並重跑 S05、S06；原投稿還沒分析完 → 延後到下一輪；原投稿沒有事件 → 補件照一般文章分析，原投稿作為第二份證據（P8-T08）。

## §6 風險模型、證據查證與發布政策

§6.1 五維風險模型、§6.2 三種判斷不變。

### §6.3 生命週期（新增部分）

- **事件合併**：被併入的事件轉為 `archived`，以 `event_merges`（被併入事件唯一）導向目標事件；不新增事件狀態（P8-T01）。
- **系列成員**：事件建立後由 S11 歸入一個系列（method ai／fallback／manual／rule），每個事件只自動歸組一次；拆出、解散、改判 false、被合併時離開系列並寫入 `event_series_removals`（reason split／dissolve／false／merged）；拆出或改判 false 的事件各自成為 1 件的系列，**拆出後不再自動歸回**；件數 0 的系列刪除（ADR-0020 決策 1）。
- **系列分析**：`series_analyses` 只新增不修改，狀態 ok／abstained／failed，每系列每台北日最多一次（失敗與 abstain 也算）；系列名稱來源 `title_source` first_event／ai／manual，人工改過的名稱不被 S12 覆蓋。
- **地點判斷**：`location_resolutions` append-only（decision alias_of／inside_of／new／split），最新一筆為目前狀態；使用者拆開（split）後不再自動合併。
- **通知遞送**：`alert_deliveries` 新增 `attempts`、`next_attempt_at`；第 3 次重試仍失敗就清除下次時間（停止）。
- **公開內容**：`publications` 的對象改為事件或系列恰好一個（`event_id`／`series_id`）；版本快照、下架、重新上架規則與事件相同。

### §6.4 自動公開策略（取代 v1.1 的表格）

公開與否仍只由公開規則引擎的確定性規則判斷（`app/publishing/policy.py`，`config/publish-policy.yaml` `policy_version` 2026-11-10.1），不由模型決定，也不需要使用者逐筆核可。

| 情境 | v1.2 公開處理 | 依據 |
| --- | --- | --- |
| 官方來源證實，或使用者查證為 true | 快報公開標題、AI 摘要、地點、日期、風險分級、官方來源，標「已查證」 | 不變 |
| 未查證（含低風險、沒有風險評估）、disputed | **公開 AI 摘要並標「尚未查證」**（不再有「只公開中性提醒」與「不公開」兩檔，移除 `safety_notice_levels`） | ADR-0018 2-1 |
| 改判 false、封存、排除類別（none） | 不公開；已公開的撤下 | 不變 |
| 疑似指控（指控規則命中） | **照原文摘要公開**、標 `needs_review`；公開或內容改變時在通知中心「公開提醒」區塊提醒使用者並附一鍵下架 | ADR-0018 2-2 |
| 改善建議 | 在系列頁公開，**不寫依據的原因**；依未確認推測原因的舊小報告措施仍不公開 | ADR-0018 2-3 |
| 推測的規律與可能原因（S12） | **只在系列分析頁公開**，一律帶「推測，尚未查證」；人工確認的原因改標「已確認」；首次公開或內容改變時在通知中心提醒並附一鍵下架；提到特定個人、群體、店家或單位（`mentions_party`，指控規則的對象關鍵字）的比照疑似指控處理，提醒中特別註明 | ADR-0020 決策 2 |
| 系列頁的其他內容 | 只依**公開中的子事件**組出（下架的子事件立即消失）；件數、每週時間軸、突增週、前後比較由程式依公開子事件重算；引用改為公開的快報 ID | P8-T06 |
| 系列頁不公開的部分 | 逐字證據、證據 ID、`to_verify`、建議依據的原因、突增的 AI 解釋、前後比較的變化比例 | P8-T06（AI 決定） |
| Facebook、匿名投稿與補件 | 只透過 AI 摘要呈現；原文、摘錄、連結、發文者、收據碼永不公開；來源欄只列官方來源 | 不變；ADR-0018 2-4 |
| S14 效益評估 | 永不公開（不進入公開快照） | ADR-0019 1-4 |
| 所有公開文字 | 一律經 `mask_pii()` | 不變 |
| 下架 | 事件與系列都可一鍵下架，即時生效並寫稽核；已下架不被同步覆蓋 | 不變 |

**硬性邊界**（寫在程式裡、設定無法關閉；AGENTS.md 已同步）：公開內容一律經 PII 遮蔽；未查證內容一律帶「尚未查證」標籤，不得呈現為已核實；疑似指控公開時必定產生提醒與下架入口；推測原因與規律只能出現在系列分析頁並帶「推測，尚未查證」，首次公開或內容改變時必定提醒；Facebook 來源只公開 AI 摘要，匿名投稿原文永不公開。

公開提醒不另建資料表：新版本中需要注意的內容（`review_parts()`：疑似指控的文字、推測的規律與原因）和目前版本不同時，版本 reasons 加 `remind`，由 `GET /api/v1/admin/publications/reminders` 列出。

## §8 事件關聯、趨勢與 What-if

### §8.1 關聯分類

不變。合併事件時，關聯改指向目標事件（連到目標本身的刪除；同一對事件同類型只留一條，已有人工決策的優先）。

### §8.2 趨勢預警

偵測規則與門檻不變。差異（P8-T03）：週／月件數 views 改為依**代表地點**分組（migration 0021，沿 `canonical_id` 找到最上層；上層地點 `parent_id` 不併入計數），並排除被合併的事件。回測（P6-T04）不分地點，不受影響。

### §8.3 情境模擬

引擎公式、Monte Carlo 與敏感度不變（G7-1 測試不修改）。差異：

- **時間窗、類別、地點**（P8-T09，取代 v1.1 D29）：自動計算歷史基準 = 歷史期間件數 ÷ 週數 × 時間窗天數 ÷ 7；歷史期間最多 52 個完整週、進行中的週不列入；地點的別名換成代表地點；沒有歷史資料時須手填；手改值優先；結果記錄 `baseline_source`（manual／auto）與依據。
- **依建議評估**（P8-T15，ADR-0019）：What-if 頁分成「依建議評估」與「自訂措施」（原 P7-T03 模式）兩個分頁。從系列分析頁的「評估效益」進入（`/admin/scenarios?series=<id>`），使用者只勾選最新一次系列分析的改善建議，不輸入數字；S14 輸出改善百分比區間（0 ≤ low ≤ high ≤ 80，證據不足時 null）、改善前／後情境、涵蓋與未涵蓋的原因、重疊、風險（≥ 1 項）、補強建議（只能引用未被選的建議）。
- 業務驗證：沒有勾選不呼叫模型；引用不存在的建議或原因被拒；有推測原因時不得寫成已確定（固定詞表）；失敗依 Runner 規則重送，仍失敗顯示「這次評估不出來」。
- 件數由程式換算：系列基準 ×（1 − 百分比），時間窗 90 天；歷史件數少於 5 件時不換算（`config/impact.yaml`）。
- 同一系列、同一次分析、同一組選擇沿用既有結果；系列分析更新後舊評估標示過期。結果存 `impact_evaluations`（不擴充 `scenario_runs`，避免影響 G7-1）。
- 頁首「假設情境，非成效預測」與「AI 估計，非實證」標籤維持平實。

### §8.4 系列事件（新增）

- **歸組**（P8-T04，S11）：候選為同類別、不是該事件離開過的系列，依事件向量距離最多 10 個，各附最近 3 起的標題、摘要與日期，不含地點；沒有候選、abstain、失敗或目標不在候選中時建立 1 件的新系列。1 件顯示為「單一事件」，2 件以上顯示「XX 系列 · 第 N 起」。
- **使用者調整**：拆出子事件（自成 1 件的系列，不再自動歸回）、解散系列、改名（`series.rename`）。
- **分析**（P8-T05，S12）：輸入最近 30 起子事件、最多 30 份證據（`<untrusted_source>`）、程式算的最近 26 週件數與突增週；突增由程式（P6-T03 規則）判斷，模型只解釋；新事件加入後由 Celery 任務分析，每系列每台北日最多一次，受每日費用上限。
- **時間軸**：日／週／月、範圍 1M／3M／6M／1Y／全部、4 期移動平均、措施第一次「處理」與「改進」的標記；後台可依地點篩選。
- **前後比較**：措施開始處理前後各 8 週的每週平均，任一邊少於 5 件只顯示「資料還不夠」，一律附「變少不一定是措施的功勞」；公開頁不顯示變化比例。

### §8.5 地點判斷與代表地點（新增）

- **S13**（P8-T02）：S02 抽出沒見過的地點名稱時，與最多 20 個代表地點比較，判斷 alias_of／inside_of／new；同名稱沿用不重複呼叫；「全校」「校外」直接建立、不判斷；abstain 或失敗當成新地點。後台可拆開判斷錯的別名。既有地點以 `uv run python -m app.locations.resolver backfill` 補判。
- **校園地點清單**（P8-T14，使用者 2026-11-05 要求；修正 ADR-0018 1-5「不建立地點清單」）：`config/locations.yaml`（正式名稱、平面圖代號、別名、上層地點，來自 2024-08 校園導覽圖與現有事件地點）以 `uv run python -m app.locations.seed` 匯入；清單內名稱直接沿用、不呼叫 S13；清單外的新名稱照 S13 判斷；使用者拆開過的不覆蓋；可重跑。2026-11-05 已匯入正式資料庫（地點共 200 筆）。
- 代表地點用於再發生、突增、CRI 的重複事件比例與 What-if 基準；上層地點只用於系列頁與後台篩選，不併入計數。

## §15 校園韌性指標

公式、錨點、樣本門檻不變。差異：

- 說明改為白話：「學校遇到狀況時，處理得好不好？」；四個構面改為四個問題（「出事後，多快有人知道？」「知道之後，多快開始處理？」「開始處理後，多久恢復正常？」「同樣的事，有沒有一再發生？」），並明寫「幾天算好是本專題自己訂的目標，不是學校的官方標準」（ADR-0020 決策 5）。
