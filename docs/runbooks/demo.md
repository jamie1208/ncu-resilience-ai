# 示範環境（P9-T01，ADR-0022）

以虛構資料跑真實流程，完整展示所有功能（含韌性成績單）。示範環境是**另一整套容器**（compose project `ncu-demo`），有自己的資料庫、Redis 與 volume，和真實環境（`ncu-resilience`）不共用任何資料，兩邊可以同時開。

## 指令

| 指令 | 作用 |
| --- | --- |
| `make demo-up` | 建置並啟動示範環境，清空示範資料庫後重新播種 |
| `make demo-seed` | 只重新播種（回到初始示範狀態）；播種期間會暫停 worker、beat |
| `make demo-down` | 停止示範環境，保留示範資料 |
| `make demo-drop CONFIRM=yes` | 刪除示範環境的容器、volume 與映像（只有 `ncu-demo_*`） |

回到真實環境不用做任何事：`make up-local` 的那一套從頭到尾沒有被碰過。

第一次使用前，在 `.env` 設定 `DEMO_ADMIN_USERNAME`、`DEMO_ADMIN_PASSWORD`（範例見 `.env.example`），這組帳密只存在示範資料庫。

## 分享給組員（ADR-0022 決策 9）

| 指令 | 作用 |
| --- | --- |
| `make demo-share` | 開放：建立臨時網址並印出來，例如 `https://xxxx.trycloudflare.com`（公開站）與 `…/admin`（示範後台） |
| `make demo-share-url` | 查目前的分享網址；沒有開放時會說明 |
| `make demo-unshare` | 關閉：停止通道，網址立即失效；示範站在你電腦上照常運作 |

- 每次 `make demo-share` 網址都會變，要重新發給組員。
- 組員用示範帳號登入後台（`DEMO_ADMIN_USERNAME`／`DEMO_ADMIN_PASSWORD`）；大家共用同一個帳號，彼此的操作互相看得到。示範完執行 `make demo-seed` 還原。
- 分享期間示範站仍用真實模型：重新分析、拆分事件、新的 What-if、匿名回報會花錢，上限是每天 `config/llm.yaml` 的 `daily_usd`（示範與真實環境分開計算）。
- 登入失敗太多次會暫時鎖住示範帳號；`make demo-seed` 會重設並解鎖。
- 電腦或 Docker 重開後分享會自動關閉，需要時再執行 `make demo-share`。
- **和真實網站的開關分開**：真實網站用 `bash infra/tunnel/tunnel.sh down`（中斷）／`up`（恢復），見 `deploy.md`；`make demo-share`／`demo-unshare` 不會動到它。真實後台不經任何通道對外。

## 網址（本機）

- 公開網站：<http://127.0.0.1:8089/>
- 管理端：<http://127.0.0.1:8089/admin>（用示範帳密登入）

請用 `127.0.0.1`，不要用 `localhost`：瀏覽器的 cookie 依主機名稱區分，真實環境用 `localhost:8088`，兩邊的登入就不會互相蓋掉。

## 隔離保證

- 種子（`python -m app.demo.seed`）只在 `NCU_ENVIRONMENT=demo` 且資料庫名稱以 `_demo` 結尾時執行，否則拒絕。
- 示範環境的 db、redis 不對主機開埠；api 8001、web 8089 只綁 127.0.0.1；不接真實網站的 tunnel（`infra/tunnel/` 只指向真實環境），只有 `make demo-share` 會開自己的臨時通道。
- 所有示範來源都是停用狀態，排程不會擷取任何真實來源；worker 不掛載 `data/`，不讀 Facebook 匯入檔。只有內部的「匿名回報」收件匣保持啟用。
- 不啟動 Prometheus、Grafana。

## 會看到什麼

約 60 個虛構事件、5 個系列，時間分布在播種日往前約 4 個月。主軸是**腳踏車失竊**（41 件）：

- 改善前：宿舍區車棚密集失竊，每週約 3 件；
- 56 天前「宿舍區車棚加裝監視器與照明」開始處理、35 天前完成；
- 改善後：系列頁的「措施前後比較」顯示前後 8 週每週件數從約 3.3 件降到約 1.6 件（約 -50%）；依地點篩選宿舍區車棚時，改善後只剩 2 件，未達 5 件的門檻，會照實顯示「資料還不夠」；
- 竊案轉移到總圖前車棚：9 天前一晚 5 件，觸發突增與趨勢解讀；剛開始處理的「總圖前車棚比照加裝監視器」照實顯示「資料還不夠」。

各頁內容：

| 頁面 | 示範內容 |
| --- | --- |
| 事件工作台 | 已查證、未查證、官方澄清為不實的事件；同一事件多篇來源；風險分級 |
| 通知中心 | 高風險通知、澄清後撤回的通知、疑似指控（店家）公開提醒與一鍵下架 |
| 事件關聯、地點 | 相關事件的關聯；「女十四舍車棚」由 S13 判為「宿舍區車棚」的別名 |
| 系列 | 腳踏車失竊（時間軸、措施標記、改善前後比較、近期突增、規律、推測原因已人工確認、其餘建議的效益評估）等 5 個系列 |
| 改善追蹤 | 從發現、處理、恢復到改進的措施，含放棄的措施 |
| 韌性成績單 | CRI 四構面都有分數；宿舍區車棚與男九舍熱水「改善後再發生」的再發生提醒 |
| What-if | 總圖前車棚腳踏車失竊的情境模擬與 AI 說明；趨勢解讀抓到總圖前車棚的突增 |
| 匿名回報 | 一則已進入事件、一則判斷不是事件 |
| 運維、Skills | 每個來源約 4 個月的擷取紀錄（含偶發失敗），各 Skill 的執行紀錄 |

種子用的 AI 回應是預先寫好的劇本（`backend/app/demo/responder.py`），不呼叫任何 API。**在示範站上的新操作**（送出匿名投稿、重新分析、新的 What-if）會使用 `.env` 的真實模型設定，會產生費用，上限沿用設定檔。

## 注意

- 每次 `make demo-up`／`make demo-seed` 都會清空示範資料庫，示範站上做過的操作都會消失。
- 日期以播種當天為準；過了幾週後「近期突增」會變成過去，重新播種即可。
