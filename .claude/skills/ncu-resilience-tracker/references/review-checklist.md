# 審視檢查清單

審視報告的「風險與偏離規格」段落依此清單逐項判斷。只寫有發現的項目；每項附證據（檔案路徑、指令輸出或紀錄位置）。

## 1. 流程紀律
- 有沒有任務標記 done 卻沒有對應的驗收紀錄（`docs/progress/records/{ID}-*.md`）？
- 後面階段已開工，但前一階段閘門未全部 pass？（tracker status 的「警告」）
- 標記 `human: true` 的任務，是否有證據顯示使用者本人做了決定（紀錄中的「需要人工決定的事項」已填寫結論）？
- 有沒有測試被刪除、跳過（`skip`、`xfail`）或門檻被調低？用 `git log -p -- '*test*'` 與 eval 設定確認。

## 2. AI Skills 品質（本專案重點）
- 每個已建立的產品 Skill：frontmatter `name` 與資料夾一致、有 `metadata.version`、有 output schema、golden cases ≥ 20 且含對抗案例、有評測報告。
- 評測報告的版本是否與 SKILL.md 目前版本一致？SKILL.md 改過但沒重跑評測 → 列為風險。
- 標記資料集是否經人工確認？若只有 AI 預標，評測結果不可作為閘門依據。
- 評測集是否依事件／時間切分？同一事件的轉載不可同時出現在 dev 與 test。
- 模型名稱是否只出現在設定檔？`grep -r "gpt-" backend/app skills` 不應命中業務邏輯。
- 數值計算（風險加權、What-if）是否由程式完成，而非由模型直接輸出最終分數？

## 3. 安全與發布（規格 §6.4、§7）
- `AUTO_PUBLISH_ENABLED` 是否在 P3-T09 對抗測試通過前就被開啟？
- 公開 API 回應是否可能含原文、投稿資訊或內部風險欄位？
- 匿名通報是否只存 receipt token 的雜湊、原文是否加密？
- 有沒有金鑰、`.env` 或個資被提交進 git？

## 4. 規格一致性
- 資料表、狀態機、API 路由是否與規格 §6.3、§9、§10 一致？若刻意偏離，是否記錄在 `docs/decisions/` 的 ADR？
- 規格要求但計畫外新增的功能，是否擴大了範圍？

## 5. 下一步建議的判斷順序
1. 修復不一致與失敗的閘門（避免在壞地基上繼續蓋）。
2. 完成進行中的任務。
3. 依 tracker 推薦的可做任務，優先選擇解鎖最多後續任務者。
4. 需要使用者決定的事項列在最後，寫清楚選項與影響。
