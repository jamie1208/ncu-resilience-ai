# 標記規範（P1-T09）

這份規範定義人工標記的欄位與判斷準則。標記結果是 S01–S06 評測的金標準（規格 §14），所以**每一筆都必須由你本人確認**；匯出時預填的值只是建議。

- 依據：ADR-0009（分類法、真偽、同事件判準，使用者 2026-10-18 決定）、規格 §6.2、§8.1、§14
- 欄位定義：`data/labeling/label.schema.json`（由 `backend/app/labeling/models.py` 產生）

## 流程

在 `backend/` 執行：

```bash
# 1. 匯出尚未標記的文章（含規則式預標），輸出到 data/raw/labeling/（不進 git）
uv run python ../scripts/labeling/export_for_labeling.py --limit 100
#    只匯出特定來源：--source facebook --source ncu-announcements

# 2. 用 Numbers 或 Excel 打開 CSV，逐列填寫標記；確認的列在 confirm 欄填 y，存成 CSV（UTF-8）

# 3. 匯入。只要有一列不合格，整個檔案都不匯入，錯誤訊息會指出第幾列、哪個欄位
uv run python ../scripts/labeling/import_labels.py ../data/raw/labeling/batch-20261018-1305.csv

# 4. 統計與切分（G1-5 需要 ≥ 100 筆）
uv run python ../scripts/labeling/dataset_stats.py --write-split --check-min 100
```

- 標記存在 `data/labeled/labels.jsonl`，**只存文章 ID、內容雜湊與標記，不存內文**。
- 匯出的 CSV 含內文，匯入完成後可以刪掉。
- 同一篇重新標記、再匯入一次，以新的標記為準。
- confirm 欄留空的列會略過，可以分好幾次標完一個檔案。

## 欄位

| 欄位 | 填法 | 必填 |
| --- | --- | --- |
| `is_campus_relevant` | y／n：內容是否與中央大學校園（師生、建築、周邊生活圈）有關 | ✅ |
| `category` | 下方 9 類之一；與校園無關時可留空，視為 `none` | 有關時 ✅ |
| `claim_type` | `official`／`first_hand`／`hearsay`／`rumor` | ✅ |
| `verification` | `verified`／`unverified`／`disputed`／`false`；非事件留空 | 事件 ✅ |
| `event_group` | 事件代號；非事件留空 | 事件 ✅ |
| `related_groups` | 相關事件的代號，以分號分隔 | |
| `high_risk` | y／n，留空視為 n | |
| `mentions_person` | y／n，留空視為 n | |
| `tags` | 補充細節，以分號分隔，最多 10 個、每個 20 字以內 | |
| `confirm` | 確認這一列的標記正確，填 y | ✅ |

**不要新增欄位**（例如備註）。匯入時會拒絕任何未定義的欄位，避免個資進入標記檔。

## 1. 是否與校園相關（`is_campus_relevant`）

- **y**：
  - 影響中央大學師生、校內建築或服務；
  - 發生在校園或周邊生活圈（中大路、宵夜街、後門一帶）；
  - 校方發布的一般公告、活動宣傳也算相關，類別是 `none`。
- **n**：
  - 跟中央大學無關的新聞或貼文，例如他校消息、全國性新聞，且沒有提到對本校的影響；
  - 廣告、徵人、二手買賣。
- 桃園市的天氣特報算相關（會影響到校），類別是 `weather`。

## 2. 類別（`category`）

一篇只選一類。看**事件本身是什麼**，不是看誰發布的。

| 代碼 | 類別 | 包含 | 不包含 |
| --- | --- | --- | --- |
| `facility` | 設施與營運 | 停水停電、施工、網路或系統中斷、電梯或空調故障、漏水 | 施工造成的道路封閉 → `traffic` |
| `weather` | 天然災害與氣象 | 颱風、豪雨、地震、高溫、寒流、淹水 | 颱風造成的停課公告 → 仍是 `weather` |
| `security` | 治安與財物 | 失竊、詐騙、可疑人士、騷擾、偷拍 | 釣魚信、帳號盜用 → `infosec` |
| `traffic` | 交通與停車 | 車禍、道路封閉、拖吊、接駁車異動、交通管制 | |
| `health` | 健康與食安 | 食物中毒、傳染病、實驗室化學品外洩 | |
| `fire` | 火災與緊急意外 | 火警、瓦斯外洩、爆炸、人員受傷的意外 | |
| `academic` | 教務與課務異動 | 非天災原因的停課、補課、調課、考試異動 | 選課、獎學金等例行公告 → `none` |
| `infosec` | 資訊安全 | 帳號盜用、釣魚信、惡意程式、個資外洩 | 系統維護停機 → `facility` |
| `none` | 非事件 | 一般公告、活動宣傳、學術新聞、徵才、閒聊、心得 | |

**同時符合多類時**：依「原因」歸類，細節放在 `tags`。例如颱風造成停電，類別是 `weather`，tags 寫「停電」；實驗室火警造成停電，類別是 `fire`。

**判斷是不是事件**：有具體的時間、地點與發生的事，而且會影響到人，就是事件。「下週三圖書館閉館整理」是 `facility` 事件；「歡迎參加校慶音樂會」是 `none`。

## 3. 陳述性質（`claim_type`）

| 代碼 | 意義 | 例子 |
| --- | --- | --- |
| `official` | 官方單位以正式管道發布 | 校方公告、氣象署特報、校方新聞稿 |
| `first_hand` | 發文者親身經歷或親眼看到 | 「我的腳踏車在宿舍前被偷了」 |
| `hearsay` | 轉述他人說法或轉貼 | 「聽說工五停電」、轉貼別人的貼文 |
| `rumor` | 沒有依據的傳聞、明顯的玩笑或惡作劇 | 「據說明天會停課（沒有任何公告）」 |

## 4. 真偽（`verification`）

依**目前蒐集到的全部證據**判斷（不只看這一篇），同一事件的文章應該填相同的值。

| 代碼 | 意義 |
| --- | --- |
| `verified` | 有官方來源，或兩個以上互相獨立的第一手來源一致 |
| `unverified` | 只有單一來源，或只有轉述，無法確認 |
| `disputed` | 來源之間互相矛盾，目前無法判斷 |
| `false` | 有官方澄清或明確證據證明不實 |

- 官方公告本身預設 `verified`。
- 官方之後發布更正時，原本的事件仍是 `verified`，tags 加上「已更正」；如果官方表示事件根本沒發生，改為 `false`。
- 不確定的時候填 `unverified`，**不要猜**。

## 5. 同事件與相關事件（`event_group`、`related_groups`）

**代號格式**：小寫英數字與連字號，64 字以內。建議格式是 `evt-日期-地點-類型`，例如 `evt-20261020-ee5-power`。代號裡**不要放人名**。

**同一事件**（填同一個 `event_group`）：類別相同、地點是同一棟建築或同一區域，而且符合以下任一條件：

- 官方公告：公告的影響期間有重疊。例如同一次停電的預告、更新與恢復通知。
- 社群或其他來源：發生時間相差 48 小時以內，而且描述的是**同一件事**，例如同一台車、同一次停電。

**相關事件**（填在 `related_groups`）：地點或時間相近，但無法確定是同一件事。例如同一週在不同宿舍發生的兩起失竊，各自有自己的 `event_group`，再互相填進對方的 `related_groups`。

同一事件的轉載、更新都要用同一個代號。切分 dev／test 時，同一個代號的文章一定會放在同一邊。

## 6. 高風險（`high_risk`）

假設事件屬實，下列任一情況就填 y：

- 可能造成人身傷害，例如火警、化學品外洩、食物中毒、可疑人士持械；
- 全校性或整棟建築的重要服務中斷半天以上，例如停水停電、網路全斷；
- 需要師生立即採取行動，例如颱風停課、緊急疏散。

高風險案例的召回率門檻是 0.95（規格 §14），判斷有疑問時偏向填 y。

## 7. 點名個人或店家（`mentions_person`）

內文中指名道姓，或可以辨識出特定個人或店家（姓名、綽號、系級加特徵、店名）就填 y。這個欄位用來測試 P3 的通知規則：點名的指控不能被寫成事實。**標記本身不要抄寫任何名字。**

## 8. 個資

- 標記檔不存內文，但 `tags` 和 `event_group` 是你自己輸入的，**不要寫人名、學號、電話、帳號**。
- 匯出的 CSV 含內文，只放在 `data/raw/labeling/`，不要複製到其他地方，也不要提交進 git。

## 9. 切分與數量

- `dataset_stats.py --write-split` 依事件組和時間切分：各組依最早發布時間排序，最晚的 30% 組放進 test，其餘放 dev。沒有發布時間的組一律放 dev。
- G1-5 要求至少 100 筆人工確認的標記。規格 §14.1 建議之後擴充到 300–500 筆，並涵蓋：正常公告、真實事件、謠言、相似但不同的事件、跨站轉載、時間地點模糊、來源衝突與惡意貼文。
- 目前的資料以官方公告為主，類別會偏向 `none` 和 `facility`。Facebook 樣本（P1-T13）進來之後，再補上謠言、轉述與來源衝突的案例。
